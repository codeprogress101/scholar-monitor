# Supervised office release

This procedure supersedes old direct-start installers. It preserves the installed App/HTTPS supervisors and LAN data. Current baseline: release-20261012, 48 migrations; candidate: 53 migrations. Do not infer compatibility from the unchanged application version.

## Preparation (no service cutover)

1. Run `npm run build` from the repository. Choose a new release directory; preparation refuses to overwrite it.
2. Run `node deployment/office-release/prepare.mjs C:/ProgramData/LDSSProduction/release-20261019-daytime`. This copies the build, migration/operational scripts, required authenticated help document and deployment tools outside the web root, installs production dependencies from the lockfile and writes a frozen SHA-256 manifest. No private environment or database records are copied into the release. Paths below use the daytime-exception candidate; earlier packages remain historical evidence.
3. Run the staged `deployment/office-release/release-helper.mjs rehearse` using Node. It reads the private production settings, creates an encrypted target backup, upgrades only a restored copy, compares all original column values, tests restored role accounts, demonstrates old-runtime incompatibility and restores a second old-schema copy for recovery. Disposable passwords and sessions exist only in those copies. The backup briefly takes source-schema read locks; coordinate this with operators if they are entering records.
4. Freeze source and run `npm run test:uat` with a new `LDSS_UAT_OUTPUT` directory. Then run the staged helper `bind-gate <absolute F36-report.json path>`. It requires the staged build, packaged source and migrations to match the successful gate. If it rejects a mismatch, stage a new directory and repeat the rehearsal. Never edit a frozen release in place.
5. Complete a private copy of `launch.example.json`. Record actual owners, two PC names, a dated window of at most two hours, manifest hash and matching private rehearsal/acceptance files. After-hours remains the default. An explicitly authorized daytime exception additionally requires `allowDaytimeMaintenance: true`, `usersSignedOutConfirmed: true` and a non-placeholder `daytimeApprovalReference`. The user requested immediate daytime maintenance and confirmed sign-out on 19 October; this does not waive artifact, backup, identity, time-window or acceptance checks. Record separate protected recovery-key custody by reference; never put key material in the launch file. Unfilled examples cannot pass preflight.

Evidence is private under `C:/ProgramData/LDSSProduction/go-live-20261019/<release>/`. Keep recovery keys separately. No source commit, production account reset or approval is generated by these tools.

## Approved cutover (Administrator PowerShell)

Notify all operators, finish work and ensure everyone signs out before stopping the app. Run the staged installer only during the recorded window:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File C:\ProgramData\LDSSProduction\release-20261019-daytime\deployment\office-release\install.ps1 -Release C:\ProgramData\LDSSProduction\release-20261019-daytime -LaunchFile C:\PRIVATE\launch.json
```

The installer checks supervised task identity, captures configuration/task definitions, disables backup/app tasks, stops the app and verifies port 3002 is free. The helper creates and verifies a fresh backup, rechecks the maintenance window, upgrades the exact 48-to-53 history, compares original business values, records grants, and runs unauthenticated readiness/security checks. It then advances only App.WorkingDirectory and the backup runner; HTTPS settings, task identities and triggers are preserved. Live authenticated checks are performed by the actual account holders after installation; the helper never resets their passwords.

Failure during migration leaves the application stopped. MariaDB DDL is not transactionally rolled back; do not blindly retry or restart the old application against an upgraded/partially upgraded schema. Inspect evidence and recover through the procedure below. Backup scheduling is re-enabled in the installer's finally block.

The installed status means restricted pilot pending, not office-wide acceptance. No firewall, router, DNS, certificate or account-role changes are made. Sign-out and limiting pilot users are operator controls, not a newly implemented access whitelist.

## Backup target and monitoring

The existing backup task polls every 30 minutes and depends on ADMIN sign-in. The new wrapper requests backup at three hours, leaving nominal headroom below the four-hour recovery-point target. Failures, host outages and delayed cloud sync can still breach that target. Task exit 2 and `C:/ProgramData/LDSSBackupStatus/go-live-monitor.json` require operator attention; task success is not proof of cloud delivery.

Keep an operator-recorded `offhost-proof.json` in that private status directory, with `sha256`, `backupCreatedAt`, `confirmedAt`, `confirmedBy`, `offHostLocation`, `retrievedFile` and `restoreReportFile`. Obtain the archive from an independently verified remote copy, verify/restore it using the established backup tooling, and use that report's hash/date. The watcher authenticates the retrieved archive and checks the matching successful restore report; it never treats desktop staging as delivery. Location and custody are operator-attested, not automatically detected.

At the three-hour warning, verify remote delivery or copy the encrypted archive to approved separate media/computer and verify retrieval; keep the key separate. If independent recoverable data is four hours old, pause new operational writes and resolve the backup gap before continuing. Check at opening/closing for the first five working days and review every warning when issued. Do not claim an unattended four-hour guarantee while desktop synchronization relies on sign-in.

## Recovery

Preserve the affected database and logs. The old application's exact-schema readiness rejects the upgraded database; application-only rollback is not assumed safe. Restore the verified pre-update archive into a **new** isolated database and verify original schema, rows and old-runtime readiness. Compare any post-backup writes with the Coordinator. Do not overwrite the only live database, reverse official history or silently lose newer transactions.

To return to the prior release, the technical owner must review a controlled database-target change: restricted runtime grants for the recovered database; matching application/backup/diagnostic configuration; the prior supervisor directory; and health/role checks before reopening. The current readiness probe deliberately pins the production database name, so it must be adapted through a separately reviewed recovery change for an alternate database. This installer does not automate that switchover. Rehearsal measures restoration/readiness, not a completed live recovery cutover. If repair/recovery cannot finish within the window, keep writes closed and communicate downtime; target recovery remains within one working day.
