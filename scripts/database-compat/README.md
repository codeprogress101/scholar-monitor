# DB-COMPAT-1 isolated compatibility artifacts

These files are proposals and rehearsal tools. They do not authorize primary or operational installation.

The five generated expressions retain NULL routing, `ascii_bin`, widths, stored/virtual kinds and every existing key/constraint. `RTRIM` removes CHAR padding at its input boundary. For `context_key`, both the tested value and its NULL condition use RTRIM so MariaDB's SQL-mode validator accepts the complete expression. Non-UUID short CHAR values under PAD_CHAR_TO_FULL_LENGTH can produce a shorter VARCHAR context key than the old mode-dependent expression; normal source mode and all stored UUID context values are unchanged. Do not assert universal expression byte equivalence under every SQL mode.

`f54-logical-transfer.mjs` is a bounded, versioned adapter for an authenticated BACKUP-1 payload. It changes exactly five generated declarations and the corresponding expected schema inventory. It never rewrites INSERTs, constraints or journal data. Its transfer entry point admits only this task's 11.4.13 loopback port/datadir, creates new unpredictable schemas/accounts and removes a failed transfer. It requires complete exact values and declared schema parity. The original migration journal describes the original executed history; a separate transfer manifest records the target construction. It is not a native fresh-schema migration runner.

`mysql2-json-text.mjs` is an explicit isolated connector proposal. MariaDB 11.4's JSON metadata causes default mysql2 reads to return objects where the accepted 10.4 contract returns text. The adapter requests raw JSON text only on the declared isolated port. Primary promotion needs a reviewed application/operator connection configuration change, not an unreviewed global preload. The accepted business source is unchanged during these tests.

`test-bootstrap.mjs` is test-only. Existing business regressions normally create fresh schemas with the historical migrations, which 11.4 cannot directly execute. On a newly owned empty test target it executes all 67 original migrations unchanged in a new same-name schema on 10.4, captures it with BACKUP-1, transfers its real journal and corrected schema to 11.4, verifies complete parity, then removes the 10.4 bootstrap. Business tests then run on 11.4. It rejects partial-migration options. This does not certify native fresh provisioning or partial migration upgrade suites on 11.4.

The forward SQL proposal is outside `db/migrations`. Four ALTER statements have implicit commit behavior; no multi-statement atomicity is claimed. Before a future authorized application, take and fully restore a current encrypted checkpoint, pin source/inventory/runtime, quiesce writes and inspect each expression. After an interrupted/uncertain ALTER, inspect the committed schema prefix and exact original data; complete only the reviewed forward statements, verify all data/schema and record the new migration through approved tooling. Never replay old migrations, fabricate journal rows or downgrade. The isolated driver verified interruption after the first ALTER, forward completion and an exact ALTER rerun.

Current Windows client caveat: the 11.4 `mariadb.exe --binary-mode` preserves CRLF in piped SQL where the accepted 10.4 client strips CR. This changes literal newline/trigger bytes for a Windows dump. Rehearsals explicitly use the unchanged accepted 10.4 dump/client against the isolated 11.4 server; native 11.4 client replacement is not accepted. A separately reviewed binary-safe import/tooling package and regression is required before retiring the old client. Do not normalize stored financial/audit JSON or ignore checksum failures.
